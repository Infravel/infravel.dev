# Email and retry operations

Brevo transactional email uses `POST https://api.brevo.com/v3/smtp/email` with the server-only `api-key` header. Configure `BREVO_API_KEY`, `EMAIL_FROM=Infravel <hello@infravel.dev>`, and `LEAD_NOTIFICATION_TO` (a private staging test inbox). Both named mailboxes and bare addresses are supported. Confirm the sender is already authorized in Brevo; any required DNS change needs separate approval. No DNS changes were made here. Reference: [Brevo transactional email API](https://developers.brevo.com/reference/send-transac-email).

The quote API commits lead/outbox first. Missing mail configuration leaves notifications pending. Mail includes only a lead ID and private-workflow instruction; the customer's email is used as replyTo. Requirements, name, company, budget, and timeline stay in D1. Provider errors and response bodies are never logged or returned. A successful response must contain a nonempty messageId before D1 records `sent`; this denotes provider acceptance, not confirmed inbox delivery.

`POST /api/internal/notifications/retry` requires bearer `RETRY_SECRET` and returns counts only. Each invocation selects up to 20 due rows. An atomic SQL claim acquires a 90-second lease and increments attempts. Before sending, ownership and lease validity are rechecked. Both acknowledgment and failure updates are fenced by the attempt generation and lease validity in an atomic D1 batch, so an old worker cannot overwrite a newer attempt. Provider requests time out after eight seconds. Failed claims never send. Failed acknowledgment bookkeeping leaves either a scheduled failed row or a processing row recoverable after lease expiry. No schema migration is needed.

Retries use exponential delays (120 seconds initially, capped at one hour); a 429 Retry-After value can extend the delay, capped at 24 hours. Automatic eligibility retains the existing 23-hour age cutoff as an operational review policy, independent of any provider guarantee. Review older pending/failed/processing rows daily, as well as backlog and missing configuration. A long provider delay may move a row outside this window, requiring manual review.

There is no provider idempotency header in this integration. This is an at-least-once workflow: if Brevo accepts mail but a timeout, crash, malformed response, or D1 acknowledgment failure obscures acceptance, a later retry can send a duplicate. A lease prevents concurrent valid claims, but cannot cancel a request already accepted by the provider or guarantee that a paused worker's request has stopped after expiry. Fencing prevents stale database writes; it cannot provide exactly-once external delivery. Uncertain attempts are never silently recorded as sent. Inspect Brevo activity and D1 by lead ID before manually replaying uncertain or stale work. Do not blindly replay it.

The repository contains `.github/workflows/notifications.yml`, scheduled every ten minutes and manually dispatchable. Its job runs only when repository variable `ENABLE_NOTIFICATION_RETRY=true`; the `notifications` GitHub environment needs `NOTIFICATION_RETRY_URL=https://<staging-worker-host>/api/internal/notifications/retry` and secret `RETRY_SECRET` matching the Worker. GitHub scheduled workflows run from the default branch and can be delayed. Remote configuration/enabled status has not been verified. Wrangler has no cron trigger; this checkout does not run retries automatically. `npm run notifications:retry` is an explicit alternative with those two environment values set privately.
