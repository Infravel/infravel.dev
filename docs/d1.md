# D1 setup, backup, and recovery

Create separate staging and production databases, and replace the matching Wrangler IDs. Never bind previews to production.

```sh
npm run db:migrate
npx wrangler d1 migrations apply DB --remote
```

The first migrates local D1; the second targets staging. Production requires --env production --remote and approval. Migration 0001 creates leads, opspilot_waitlist, notification_outbox, and rate_limits. D1 batch commits lead/outbox atomically. Case-insensitive duplicate waitlist registration is a no-op and does not overwrite consent or disclose membership.

Review leads through authenticated Cloudflare tooling; no public listing exists. Review failed/pending/stale outbox rows daily. Run an operational cleanup periodically: `DELETE FROM rate_limits WHERE expires_at < unixepoch();`. Limits reset after ten minutes even before cleanup. Set owner-approved personal-data retention; proposed review of unconverted leads after 12 months and waitlist deletion when no longer needed or on request. Keep exports out of logs.

Before production changes record a Time Travel bookmark (`wrangler d1 time-travel info DB --env production`) and export with `wrangler d1 export DB --env production --remote --output=/secure/location/backup.sql`. Choose an encrypted access-controlled location outside the repository. Confirm Time Travel retention for the account/plan and set export expiry. Rehearse restoration to a separate database and compare table counts/constraints.

Emergency restore: pause submissions, export current data, then use `wrangler d1 time-travel restore DB --env production --bookmark <recorded-bookmark>` only after approval. Reconcile writes after the bookmark before reopening. Application rollback does not require database rollback; prefer additive forward-compatible migrations.
